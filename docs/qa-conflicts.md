## 27. 가입 이메일 범위

- **QA (B4)**: 아무 이메일로 가입할 수 있고 인증 코드가 필요하다.
- **지금**: `@skuniv.ac.kr`만 가입할 수 있다. 심사위원은 체험 로그인으로 들어온다.
- **추천: 학교 이메일만 유지.**
  - 아무 이메일을 허용하면 무료 메일로 계정을 수십 개 만들어 확인 질문을 나눠 시도하기 쉬워진다 (위협 모델 T8b가 바로 이 공격).
  - 위협 모델 T11·B12의 목적인 "찾아간 사람 특정"은 학교 계정일 때 의미가 있다. 아무 메일이면 특정할 수 없다.
  - 학교 밖 사람(심사위원·방문자)은 체험 로그인과 보관처 대면 문의로 충분하다.
- 학교 메일 서버가 인증 메일을 스팸 처리하는지는 확인이 필요하다 (tech-stack 10장).

## 28. 후보 개수와 근거 표시

- **QA (B5, B6)**: 상위 3개 후보와 항목별 근거를 보여 주고, 정답이 상위 3개 안에 드는 비율이 70% 이상이어야 한다.
- **지금**: 점수 상위 5개를 습득일 순으로 보여 주고, 점수·근거는 숨긴다 (#6).
- **추천: 5개 유지, 근거는 공개 정보로만.**
  - "색이 일치해요" 같은 근거는 숨긴 정보(색·특징)를 그대로 알려 준다. 근거를 보고 설명을 고쳐 맞히는 공격이 된다 (위협 모델 T3와 충돌).
  - 대신 공개 정보만 쓴 근거는 안전하다. 예: "같은 건물", "잃어버린 뒤 2시간 안에 등록", "같은 종류 / 비슷한 종류". 이건 바로 추가할 수 있다.
  - 3개로 줄이면 종류를 잘못 읽은 경우(#10)에 정답이 빠지기 쉽다.
  - 지표는 둘 다 보고한다: 내부 점수 기준 상위 3개 안 비율(QA 목표 70%)과 노출 5개 안 비율.

## 29. 확인 전 흐린 사진

- **QA (B7)**: 확인 전 후보에는 종류·날짜·건물·흐린 사진이 보인다.
- **지금**: 확인 전에는 사진을 보여 주지 않는다. 종류 아이콘으로 구분한다.
- **추천: 사진 없음 유지.**
  - 강하게 흐려도 색과 모양은 보인다. 색은 비공개 정보이고 판정의 모순 검사에 쓰이므로, 흐린 사진은 "색을 맞혀 모순을 피하는" 힌트가 된다.
  - 사진을 보고 "내 거 같은데" 하고 아무거나 시도하는 걸 줄이는 효과도 있다.
- 디자인 1회차도 이 원칙대로 나와 있다.

## 30. 통과 후 사진

- **QA (B8, B9)**: 통과하면 선명한 사진이 열리고, 원본은 서명 URL로 연다.
- **지금**: 통과하면 공개용 사진을 서명 URL(10분)로 준다. 민감하지 않은 사진은 EXIF를 지운 1024px 선명한 축소본이고, 학생증·카드·얼굴이 있으면 전체 블러본이다. 원본은 관리자만 본다.
- **추천: 구현 유지, QA 문구를 "공개용 사본"으로 수정.**
  - 판정 통과는 "주인일 가능성이 높다"이지 신원 확인이 아니다. 학생증 사진을 선명하게 보여 주면 통과만 하면 남의 개인정보를 볼 수 있다.
  - 민감한 물건은 보관처에서 대면으로 확인한다 (T11과 같은 방향).
- 이미 QA가 원하는 대부분(서버에서 만든 사본, 추측 불가 경로, 만료되는 서명 URL)은 구현되어 있다.

## 31. 잠금 단위

- **QA (B10, T8b)**: 물건 단위로 3회 틀리면 잠긴다. 계정 A 2회 + 계정 B 1회여도 잠긴다.
- **지금**: 계정마다 물건당 3회.
- **추천: 둘을 합친다.**
  - 계정당 물건당 3회는 그대로 둔다.
  - 여기에 **물건 합계 실패 상한(예: 10회)**을 더한다. 넘으면 그 물건은 앱에서 공개하지 않고 "보관처에서 대면 확인" 상태로 바꾸고 관리자에게 알린다.
  - 물건 단위 3회만 쓰면 공격자가 일부러 3번 틀려 진짜 주인이 영영 확인 못 하게 만들 수 있다 (방해 공격).
  - 27번처럼 학교 이메일만 받으면 계정 여러 개 만들기가 어려워서, 합계 상한은 넉넉하게 잡아도 된다.
- 구현: 판정 때 물건별 실패 합계를 같이 세면 된다. 잠금(advisory lock)은 이미 물건 단위로도 걸 수 있다.

## 32. 고가품 보관

- **QA (B11)**: 고가품은 보관 방식이 센터·경비실만 선택된다.
- **지금**: 구분 없이 `그 자리에 둠`을 고를 수 있다.
- **추천: 반영. 다만 단계적으로.**
  - 문제는 순서다. 지금은 습득자가 보관 위치를 고른 뒤 AI가 종류를 읽는다. 고르기 전에는 고가품인지 모른다.
  - P0: AI 결과가 고가품(지갑·카드·휴대폰·노트북·태블릿·이어폰·시계 등)인데 `그 자리에 둠`이면, 완료 화면에서 "가까운 보관처에 맡겨 주세요"와 보관처 안내를 보여 준다. 분실자 공개 화면에도 대면 수령 안내를 붙인다 (W3).
  - P1: 사진을 먼저 올려 AI가 돌아가는 동안 건물을 고르게 하고, 결과가 나오면 고가품일 때 `그 자리에 둠`을 막는다. 등록 API를 두 단계로 나눠야 한다.
- 고가품 목록은 36번 분류가 정해지면 같이 정한다.

## 33. 데이터 삭제

- **지금**: 수령 30일 뒤 시도·열람 기록만 지운다. 사진과 습득물 정보는 남는다 (#12, #26).
- **추천: 반영.**
  - 개인정보 최소 보관은 심사에서 설명하기 좋은 포인트이고, 구현도 어렵지 않다 (정기 작업이 이미 있음).
  - 수령 완료 시: 스토리지 원본·공개본 삭제, 비공개 속성·설명·임베딩 비우기. 종류·건물·날짜·상태는 통계(F-15)를 위해 남긴다.
  - 미수령 30일: 상태를 `기한 만료`로 바꾸고 같은 방식으로 지운다. 실물은 보관처가 따로 관리한다.
  - 시도·열람·수령 기록: 수령(또는 만료) 30일 뒤 삭제. 26번(수령 기록 보관 기간)도 이걸로 정리된다.

## 34. 좌표 처리

- **QA (B14, T5)**: 사진 GPS → 브라우저 위치 → 직접 선택 순서로 건물을 추천한다. 좌표는 브라우저에서 건물로 바꾸고, 서버 요청·DB·로그 어디에도 남기지 않는다. 업로드 전 브라우저에서 EXIF를 지우고 서버도 한 번 더 지운다.
- **지금**: 사진 위치는 쓰지 않는다. `GET /buildings/nearest?lat=..&lng=..`로 좌표를 서버에 보내고, 요청 로그(pino-http)에 URL이 그대로 남는다.
- **추천: 반영.** QA 쪽이 개인정보 측면에서 확실히 낫다.
  - 건물 목록(`GET /buildings`)에 좌표가 이미 있으므로, 가장 가까운 건물 계산을 프론트로 옮긴다. `/buildings/nearest`는 없앤다.
  - 사진 GPS는 "물건을 주운 자리"라 브라우저 위치보다 정확하다. 브라우저에서 읽어 건물로만 바꾸고 버린다.
  - 업로드 전 canvas로 다시 인코딩하면 EXIF가 빠진다 (어차피 용량 줄이기를 하므로 같이 하면 된다). 서버의 sharp 메타데이터 제거는 이미 되어 있다.
  - 요청 로그에서 쿼리 문자열을 빼도록 로거 설정도 고친다.

## 35. 동의 화면

- **QA (B15)**: 이메일 수집, 위치 사용, 사진 외부 AI 처리 3가지를 한 화면에서 받는다.
- **지금**: 명세·화면 모두 없다.
- **추천: 반영.**
  - 외부 AI(Gemini)로 사진을 보내는 건 국외 처리라 고지가 필요하다. 심사에서도 개인정보 항목 점수와 직결된다.
  - 분실자: 가입할 때 동의를 받고 동의 버전·시각을 저장한다.
  - 습득자(비로그인): 첫 등록 때 동의 화면을 보여 주고, 브라우저에 기억한다. 등록 요청에 동의 버전을 같이 보낸다.
  - 디자인 2회차 요청에 동의 화면을 추가해야 한다.

## 36. 종류와 색

- **QA (B2)**: 종류는 LOST112 기반 서비스 분류(20개, 우산·텀블러·열쇠·필기구는 따로), 색은 LOST112 색 코드 안의 값만 저장한다.
- **지금**: 종류 10개 enum, 색은 AI가 쓴 자유 문자열.
- **추천: 반영. 단 색은 12개 기본색으로 저장.**
  - 종류: 분류가 늘면 후보가 더 정확해진다. LOST112와 맞춰 두면 나중에 공공 데이터와 연결하기도 쉽다. 연관 종류 묶음(#10)을 새 분류에 맞춰 다시 짠다.
  - 색: 123개 코드를 그대로 쓰면 AI가 비슷한 코드 사이에서 흔들린다. LOST112.md의 "UI 12색" 묶음을 저장값으로 쓰고, LOST112와 주고받을 때만 코드로 바꾼다.
  - 색을 고정된 목록으로 바꾸면 "비슷한 색은 확인 불가"(#24) 규칙도 정확해진다. 지금은 문자열 비교라 애매하다.
  - AI 응답 스키마에서 허용값 밖이면 거부하므로 T6(사진 속 글자로 조작)에도 강해진다.

## 37. AI로 보내기 전에 가리기

- **QA (B3, T4)**: 얼굴·학생증·카드번호는 저장 전, AI로 보내기 전에 가린다.
- **지금**: 원본을 AI로 보내 민감 여부를 판단하게 하고, 민감하면 공개본을 블러로 만든다.
- **추천: 절충.**
  - 무엇이 민감한지 알려면 먼저 봐야 한다. AI로 보내기 전에 가리려면 서버 안에서 따로 탐지해야 하는데, 카드번호·이름까지 정확히 찾는 건 공모전 기간에 어렵다.
  - P0: Gemini **유료 구간**을 써서 입력이 학습에 쓰이지 않게 하고(T7), 이를 동의 화면과 보고서에 명시한다.
  - P0+: 얼굴은 가벼운 얼굴 탐지 모델로 AI 전송 전에 서버에서 가린다. 학생증·카드는 AI 판단에 맡기고, 판단이 애매하면 전체 블러 (지금 규칙).
  - QA 기준표 B3 문구를 "저장·공개 전에 가린다. AI 전송은 학습 미사용 구간, 얼굴은 전송 전 가림"으로 고친다.

## 38. 제목 자동 생성, 캡차

- **QA (B1, T8)**: 등록하면 제목이 자동으로 채워지고, 비로그인 등록에 캡차가 있다.
- **지금**: 제목 없음. 등록은 기기·IP 기준 10분 5건 제한만.
- **추천: 둘 다 반영.**
  - 제목: AI 응답에 짧은 제목(예: "흰색 무선 이어폰, 곰돌이 스티커")을 추가한다. 비공개 정보가 들어가므로 **관리자 화면에만** 쓴다. 분실자에게는 종류 이름만.
  - 캡차: Cloudflare Turnstile(무료, 대부분 클릭 없이 통과)을 습득물 등록, 체험 계정 생성, 인증 코드 요청에 붙인다. 서버에서 토큰만 확인하면 된다.
